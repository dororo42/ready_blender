## 第二部分:Numba vs Blender 内置 GPU Compute Shader 路线评估

### 2.1 前提:依赖分发问题的定位

extensions.blender.org 的政策是**不允许扩展包捆绑二进制 wheel**(安全审查),但**允许扩展在运行时引导用户自行安装可选依赖**。Pro v6 的解法(AddonPreferences 镜像源选择 + pip install/update/uninstall/check 四算子)正是这个模式的实现——**分发合规问题确实可解**,"官方上架不带依赖"不构成 Numba 路线的否决项。但它只解决**分发**,不解决**兼容与维护**(见 2.2)。

### 2.2 两条路线对比

| 维度 | Numba(Pro v6 模式) | GPU Compute Shader(Blender gpu 模块) |
|---|---|---|
| **性能** | CPU 标量 JIT:边循环拓扑网格路径快 5-20x;网格大时受内存带宽限制;单线程至多 OpenMP | GPU 并行:规则网格路径快 50-500x;百万格点千步亚秒级;吞吐数量级优势 |
| **依赖** | 需用户自装(prefs 窗口+镜像源可解分发);numba/llvmlite 必须匹配 Blender 内置 Python 版本(4.x 升级期风险);离线/企业环境不可装 | **零依赖**,bl_info 即装即用 |
| **平台一致性** | CPU 结果逐位确定,跨平台一致,可直接做回归基线 | float32 舍入与 numpy 有差异(需容差断言);无 float64(消费级);**Metal(macOS)/Vulkan/OpenGL 后端行为差异**是主要风险 |
| **API 稳定性** | numba API 成熟稳定 | Blender gpu 模块 compute API 仍半内部化:4.2 起 Vulkan/Metal 后端切换期,文档稀缺,跨版本兼容成本高,`gpu.capabilities` 需运行时探测降级 |
| **规则覆盖面** | **任意规则**:标量循环天然表达 Gray-Scott/FHN/CA/公式系统;FormulaRule 可直接编译 | 规则→GLSL 代码生成:固定规则(Gray-Scott)容易,**动态公式需写 Python→shader 表达式编译器**,工程量大;CA 邻居查表受限于纹理格式 |
| **拓扑网格适配** | **优**:边循环对非规则邻接天然友好(散写无成本) | 弱:gather 模式需 K 列填充/CSR 打包进纹理缓冲,边长不均时槽位浪费,工程复杂 |
| **规则网格(2D)适配** | 良好但非最优(规则网格上 numpy 向量化已拿走大半收益) | **最优**:规则访存 + 双缓冲 ping-pong 纹理,教科书式场景 |
| **首用延迟** | JIT 编译秒级(cache=True 可缓存,参数变化不重编) | shader 编译毫秒级 |
| **调试/测试** | Python 层可断点;双路径(numba/numpy)需双份测试但逻辑同源 | GPU 错误只能运行时表面化;需保留 numpy 参考实现做容差比对(等于必然双路径) |
| **许可/上架** | 可上架(依赖用户自装) | 可上架,无任何附加条件 |
| **维护成本** | 中:两条内核(numba/numpy)同构维护 | 高:shader 版本适配 + 回退链(GPU→numpy)+ 容差测试 |

### 2.3 结论与建议架构(待确认后实施)

**两者不是二选一,而是按求解域分工**:

```
┌─ 2D 规则网格路径 ──→ GPU compute shader(规则访存,收益最大;gpu.capabilities 探测,失败回退)
│                     └ 回退→ fast_ops numpy(已有,1.9-2.5x,零依赖基线)
└─ 拓扑网格路径(面域/顶点域)──→ numba(边循环标量内核,任意邻接天然表达;prefs 安装窗口)
                          └ 回退→ 现 numpy np.add.at 路径(已有)
```

- **Numba 采纳 Pro v6 的配置窗口模式**(镜像源枚举+自定义 URL+四算子+状态显示),但做两点改良:①安装命令加 `--no-warn-script-location` 且用 `sys.executable -m pip`(v6 已如此,保持);②装完做 `import numba` 自检并报告兼容性,而非仅 pip 返回码(v6 的盲点)
- **compute shader 先行试点 2D 网格**(风险最低、收益最大),拓扑网格 GPU 化推迟到 Blender gpu compute API 稳定(建议观察 4.3/4.4)
- **回归基线永远保留 numpy 路径**:所有加速层是"可选替换内核",不是替代——这已是本项目 backend 抽象的设计初衷,方向吻合
- 分阶段:①numba 后端(低风险,覆盖顶点域新路径,与 Pro v6 性能口径对齐)→ ②2D compute shader 试点 → ③视 API 演进决定拓扑网格 GPU 化

## 第三部分:为什么"均匀稀疏种子"效果更好——原理解析

您实测"均匀稀疏(5% 随机撒点)比中央扰动效果好",根因有四层,按重要性排序:

### R-A 波前传播速度有限 → 中央种子覆盖不全(最主要)

Gray-Scott 的 b(V) 场图案靠**反应波前**向外扩张——b 从种子区边缘向外"啃食" U=1 的均匀态,扩张速度由 Du/Dv 与反应速率共同决定,是**有限速度**。以 500~2000 步典型迭代预算、每步扩张 ~1 顶点量级估算,中央块扰动的图案半径 ≈ 数十至一两百顶点,**表面大面积仍是 b=0 的空白**(U 均匀态,无任何视觉特征)。
均匀稀疏种子让**每个种子同时启动局部波前**,整体覆盖率在同样迭代预算内逼近 100%——这不是图案"更好看",而是图案**出现在了全部表面上**。

### R-B 种子间距≈自然波长 → 无长波调整期,直接进入成型态

RD 图案有参数(F/k)决定的**特征波长**(最不稳定模式的波数,linear stability analysis 的 fastest-growing mode):
- **中央大块扰动**:初始 b 场是低频成分为主的块,需要漫长的非线性演化把块"撕裂"重排成特征波长——前期大量迭代花在波长调整,成型慢且边缘遗留过渡形态
- **5% 稀疏点**:单点种子的空间谱本来就以高频为主,相邻种子间距(~4-5 顶点)已接近斑点/虫纹的自然尺度,各自**就地成核**为独立图案单元,几乎没有长波重排期

### R-C RD 系统的"密度自校正"特性 → 5% 恰在自然密度邻域

Gray-Scott 斑图有**固有面密度**(由 F/k 决定的斑点/条纹自然密度)。种子密度的影响:
- 种子过密 → 相邻图案单元竞争、合并、湮灭,浪费迭代还留下大块疤痕
- 种子过疏 → 波前未相遇,留下空白走廊
- **~5% 随机覆盖**:冗余种子湮灭、稀疏区被波前补位,系统**自组织收敛到自然密度**——初始不均匀被动力学抹平。Poisson 随机撒点的成团/空隙缺陷在 5% 密度下幅度小、且被自校正消化,所以"随机"已足够好,**无需真·蓝噪声/泊松盘采样**(若追求极致均匀可用,但收益边际递减)

### R-D 边界规避 + Dirichlet 的协同(本项目已实现的部分)

稀疏种子算法**避开边界顶点撒种**+ 边界 Dirichlet(U=1/V=0):
- 种子不落在边界 → 不会出现"半个图案"被边界切断的破相
- 边界浓度固定 → 拉普拉斯在开放边上不对称的失真被钉住,靠近边缘的图案完整
两者叠加使图案在**包括边缘在内的整个表面**都成型干净。中央扰动通常居中,离边界远,感知不到这层好处;满铺种子后边界处理立刻成为必需——这正是 v6pro 把两者绑定实现的原因。

### 小结

| 因素 | 中央扰动 | 均匀稀疏 5% |
|---|---|---|
| 覆盖率(有限迭代) | 局部(~30%↓) | 满铺 |
| 成型速度 | 慢(长波重排) | 快(就地成核) |
| 密度适配 | 与自然密度无关 | 自校正收敛 |
| 边界协同 | 无感 | 必须,且已具备 |

一句话:**稀疏均匀撒种把"演化出图案位置"的成本预付在了初始化里,让有限迭代预算全部花在"细化图案形态"上**——这是对 RD 动力学特性的正确利用,不是玄学。
